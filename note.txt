Algorithmes et règles métier à bien comprendre:

🔄 Échange en chaîne (graphe orienté)
Nœud = groupe d’un bloc.
Arête = demande en attente (groupe actuel → groupe souhaité).
Un cycle dans le graphe signifie que chaque groupe perd et gagne autant d’étudiants, donc les capacités restent respectées.
Patrick: A→B     Bob: B→C     Carlo: C→A     ⇒ cycle A→B→C→A

Algorithme : DFS par bloc, avec une limite de profondeur (par exemple 6) :

Pour chaque demande de départ, suivre les demandes dont le groupe actuel est égal au groupe souhaité de la précédente.
Quand on retombe sur le groupe de départ, on a un cycle.
Interdire de réutiliser la même demande ou le même groupe dans un cycle.
Filtrer les cycles de moins de 3 si l’énoncé l’impose (un cycle de 2 est un simple swap).

Application atomique : BeginTransactionAsync, puis revalider chaque affectation et chaque capacité dans la transaction, puis modifier, puis Commit. Au moindre échec, Rollback.

⚠️ Pour SQLite, pense à la concurrence : utilise un RowVersion ou revérifie l’état des demandes (« toujours en attente ? ») au moment de l’application.

⏰ Détection de conflits d’horaires
csharp
bool Overlap(Session a, Session b) => a.Start < b.End && b.Start < a.End;
Le calcul est 100 % C#, pur et testable, sans accès base de données dans la méthode.
Entrée : les sessions de tous les groupes de l’étudiant, tous blocs confondus, plus le groupe envisagé à la place de l’ancien.
Sortie : la liste des paires en conflit, pour que ce soit explicable (« Math mercredi 14h–16h chevauche Prog 15h–17h »).
🎲 Répartition initiale
Séparer les étudiants par catégorie virtuelle.
Distribuer chaque catégorie en round-robin sur les groupes (équité).
Répartir les autres étudiants aléatoirement, avec un Random(seed) injectable, donc reproductible en test.
Ne jamais dépasser la capacité, et lever une erreur claire si la capacité totale est insuffisante.

[Authorize] global par défaut (filtre global), avec [AllowAnonymous] uniquement sur le login.
Identity pour les comptes, avec hash de mot de passe intégré (PBKDF2).

7️⃣ Échange en chaîne

Théorie. Noeud = groupe d’un bloc, arête = demande Pending de FromGroup vers DesiredGroup. Un cycle simple de longueur ≥3 garde les effectifs : chaque groupe perd un étudiant et en gagne un. La capacité reste donc respectée automatiquement.

Algorithme (DFS limité, par bloc) :

Pour chaque demande de départ, suivre les demandes dont FromGroup égale le DesiredGroup précédent.
Un cycle est trouvé quand on revient au groupe de départ.
Ne jamais réutiliser une demande ou un groupe dans le même cycle (RG7).
Profondeur maximale d’environ 6, longueur minimale 3 (paramètre configurable).
FindCycles renvoie un IEnumerable<SwapCycle> avec yield return, exactement comme ton Yield.cs.

Application (squelette, à compléter) :

csharp
public async Task ApplyAsync(int proposalId)
{
    using var tx = await _context.Database.BeginTransactionAsync();
    try
    {
        var proposal = await _context.SwapProposals
            .Include(p => p.Items).ThenInclude(i => i.ChangeRequest)
            .SingleAsync(p => p.Id == proposalId);

        // 1. REVALIDER dans la transaction : toutes les demandes encore Pending,
        //    chaque affectation toujours dans FromGroupId, même bloc
        // 2. Recalculer les capacités après échange
        // 3. Modifier assignment.GroupId pour chaque item, statuts → Accepted / Applied
        await _context.SaveChangesAsync();
        await tx.CommitAsync();
    }
    catch
    {
        await tx.RollbackAsync();
        throw;
    }
    // 4. Notifier SignalR ICI, après le commit, hors du try
}

⏰ Conflits d’horaire

Overlap(a, b) = a.Start < b.End && b.Start < a.End. Quand une séance finit exactement quand l’autre commence, ce n’est pas un conflit.

Pour un candidat, l’horaire complet = séances de tous les groupes de l’étudiant (tous blocs), moins celles du groupe quitté, plus celles du groupe visé. La méthode est pure, donc facile à tester, et renvoie les paires en conflit pour pouvoir expliquer chaque refus.
